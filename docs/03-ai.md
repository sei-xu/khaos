# Khaos — Integração com IA

## Como funciona

A IA conversa em linguagem natural e age no banco via **tool use** —
ferramentas genéricas de leitura/escrita, não uma ferramenta por entidade.
Um único modelo (Claude) é usado; as integrações antigas com Gemini e
DeepSeek foram descontinuadas junto com o backend FastAPI que as hospedava.

```mermaid
flowchart TD
  step1["Você: 'Crie uma tarefa de design para amanhã'"]
  --> step2["Claude decide: preciso de insert_row(tasks, ...)"]
  --> step3["Tool executa contra o Supabase (client-side)"]
  --> step4["Claude responde: 'Criada.' [[task:uuid]]"]
```

Não existe um backend próprio que execute as tools — elas rodam no mesmo
processo que fez a chamada ao modelo: no navegador para o chat do app
(`src/lib/chat`), ou dentro da Edge Function `telegram-bot` para o Telegram.
Ambos compartilham o mesmo núcleo de código (ver
[Dois front-ends, um cérebro](#dois-front-ends-um-cérebro)).

## Modelo

- Modelo: `claude-sonnet-5` (configurável via `VITE_LLM_MODEL` no app,
  `LLM_MODEL` na Edge Function do Telegram)
- O oversight agent (análise em segundo plano) usa `claude-haiku-4-5` por
  padrão, configurável via `OVERSIGHT_LLM_MODEL`
- Tool use nativo via `@anthropic-ai/sdk`, chamado diretamente do client —
  não há wrapper próprio de protocolo

A chave `ANTHROPIC_API_KEY` nunca chega ao navegador: o SDK do Anthropic é
apontado (`baseURL`) para a Edge Function `anthropic-proxy`, que injeta a
chave do lado do servidor e repassa a chamada para `api.anthropic.com`. Ver
[`anthropic-proxy`](#anthropic-proxy) abaixo.

## Arquivos (app web)

| Arquivo | Responsabilidade |
| --- | --- |
| `src/lib/chat/client.ts` | Cria o client Anthropic apontado para o proxy; reexporta os prompts |
| `src/lib/chat/prompts.ts` | `TONE_INSTRUCTION` (persona) e `SYSTEM_INSTRUCTION` (regras de domínio) — puro texto, sem imports, compartilhado com o bot do Telegram (Deno) |
| `src/lib/chat/agent.ts` | Loop de turno: monta o system prompt (com cache), envia ao modelo, executa tool calls, acumula histórico até 6 rodadas de tool use por turno |
| `src/lib/chat/toolsCore.ts` | Schemas das tools, coerção de argumentos, o executor (`executeTool`) — framework-agnóstico, sem imports de runtime, compartilhado com o Telegram |
| `src/lib/chat/tools.ts` | Injeta o client Supabase (anon key) e `searchSchema` no núcleo acima, para uso no browser |
| `src/lib/chat/schemaSearch.ts` / `schemaSearchCore.ts` | Busca por palavra-chave no schema do banco (tabelas, colunas, enums, RPCs) — power por trás da tool `search_schema` |
| `src/lib/chat/entityRefs.ts` | Extrai/injeta os tokens `[[task:uuid]]`/`[[project:uuid]]`/`[[section:uuid]]`/`[[event:uuid]]` (cards inline) e `[[confirm: A \| B]]` (botões de confirmação) |
| `src/lib/chat/turnQueue.ts` | Fila FIFO serial (lógica pura, testada) para os turnos de chat — ver `useChatAgent.ts` |
| `src/lib/chat/turnPrefix.ts` | Classifica os prefixos ocultos de um turno (`[Temporal Context: ...]`, `[UI Context: ...]`, `[Session Bootstrap: ...]`, `[DB Change: ...]`) contando profundidade de colchetes, em vez de um regex ancorado no primeiro `]` — ver [Reagindo a mudanças de banco](#reagindo-a-mudanças-de-banco-fora-do-chat) |
| `src/lib/chat/history.ts` | Leitura/escrita do histórico de conversa (`chat_history`, compartilhado com o Telegram) |
| `src/lib/chat/chatActivityContext.tsx` | Contexto React para estado de atividade do chat (badge de mensagem não vista — opener ou nudge reativo) |
| `src/hooks/useChatAgent.ts` | Hook que orquestra `runTurn`, injeta contexto temporal/UI na mensagem do usuário, enfileira os turnos (`turnQueue.ts`) e monta o turno silencioso de reação a mudanças de banco |
| `src/lib/chat/changeWatcher.ts` | Lógica pura (testada, ver `changeWatcher.test.ts`) de buffering/gate/cooldown/formatação do watcher reativo de mudanças de banco — sem imports de runtime |
| `src/hooks/useDbChangeFeed.ts` | Liga `changeWatcher.ts` a uma subscription Realtime em `moments` (com fallback de poll) e à fila de turnos de chat |

## System prompt

`prompts.ts` define duas seções, montadas em `agent.ts` dentro de
`<system_instructions>` / `<tone_and_behavior>` e marcadas com
`cache_control: ephemeral` para acionar prompt caching (o texto precisa ser
byte-a-byte idêntico entre chamadas — contexto variável como data/hora vai
na mensagem do usuário, não no system prompt).

- **`TONE_INSTRUCTION`** — persona: calma, observadora, concisa; nunca
  reivindica uma ação como concluída sem que a tool correspondente tenha
  tido sucesso; regras de quando elaborar vs. responder em uma palavra;
  regras de abertura de sessão.
- **`SYSTEM_INSTRUCTION`** — regras de domínio: hierarquia
  field→project→section→task, uso de `ilike` para busca por nome, `due` vs.
  `target`, como tratar `task_logs` (foreground/background), o toggle
  "marcado para hoje" (moments `today`/`notToday`), obrigatoriedade do
  parâmetro `reason` ao mudar status/prioridade/due/estimate, o formato
  dos tokens `[[task:uuid]]` / `[[project:uuid]]` / `[[section:uuid]]` /
  `[[event:uuid]]` que a UI renderiza como cards, o token
  `[[confirm: A | B | C]]` que a UI (e, no Telegram, o bot) renderiza como
  botões — ver [Confirmação com botões](#confirmação-com-botões) — o prefixo
  `[UI Context: ...]` que a interface injeta (ver `useChatAgent.ts`) como
  sinal de onde alocar uma tarefa nova, e a regra de propor
  colocação/estimativa (`suggest_task_placement`/`suggest_task_estimate`)
  antes de criar uma tarefa sem projeto/seção explícitos.

## Confirmação com botões

Antes desta seção, uma confirmação conversacional ("confirma?",
`suggest_task_placement`, as ofertas do digest matinal) exigia que o usuário
*digitasse* a resposta — não existe, e esta mudança não ressuscita, o gate de
confirmação por tool removido no commit `3ccd29f` (ver o comentário em
`supabase/functions/_shared/khaos.ts`, "No confirmation gate" — escrita
continua direta, sem passo de confirmação a nível de tool).

O modelo agora pode fechar uma resposta com `[[confirm: A | B | C]]`
(`entityRefs.ts`, 2-4 opções, `\|` escapa um `|` literal dentro de uma
opção). No app, `ChatPanel` renderiza um botão por opção — só na última
mensagem do assistente, para um botão de um turno antigo nunca poder ser
reexecutado — e o clique manda o texto da opção como o próximo turno de
usuário, pela mesma fila (`turnQueue.ts`). No Telegram,
`buildInlineKeyboard` (`_shared/telegramRender.ts`) converte o mesmo token
num `inline_keyboard`; `telegram-bot/index.ts` trata o `callback_query` do
tap (responde, remove o teclado da mensagem, roda o agente com o label).
Uma opção cujo `callback_data` passaria de 64 bytes (limite do Telegram) não
recebe botão — a mensagem cai para "responda digitando: `<opção>`" só para
essa opção.

## Tools disponíveis

Ao contrário da versão original do sistema (uma tool por operação de cada
entidade — `create_task`, `update_project` etc.), a IA hoje opera com um
conjunto pequeno e genérico de ferramentas do tipo SQL:

### Leitura

| Tool | Descrição |
| --- | --- |
| `search_schema` | Busca por palavra-chave no schema (tabelas, colunas, enums, RPCs) |
| `query_rows` | `SELECT` genérico — tabela, `select`, `filters` (coluna/operador/valor), `orderBy`, `limit` |
| `list_tasks_marked_for_day` | Deriva quais tarefas estão "marcadas para hoje" (ou outro dia) a partir dos moments `today`/`notToday` — evita reimplementar essa lógica via `query_rows` bruto |
| `suggest_task_placement` | Devolve a hierarquia ativa (field→project→section, com contagem de tarefas abertas e última atividade por seção/projeto) para a IA escolher onde colocar uma tarefa nova sem projeto/seção informados — sem score lexical, o casamento pelo nome é feito pelo próprio modelo |
| `suggest_task_estimate` | Sugere um `estimate` em minutos a partir de `task_logs` reais de tarefas comparáveis (mesma seção → mesmo projeto → `work_tag` em comum → palavras do nome), com mediana/média e a base usada, ou `{basis:'none', n:0}` quando não há histórico |
| `suggest_next_task` | Dado o id de uma tarefa recém-assentada (ex: marcada `done`), devolve candidatos ranqueados para a próxima: sucessor desbloqueado em `tasks_sequence` → irmã aberta na mesma seção → tarefa com `work_tag` em comum → cabeça da fila `backlog_rank`, parando no primeiro nível com resultado, ou `{basis:'none', n:0}` |

### Escrita

| Tool | Descrição |
| --- | --- |
| `insert_row` | Insere uma linha em qualquer tabela permitida |
| `update_rows` | Atualiza linhas que casam com `filters` |
| `delete_rows` | Remove linhas que casam com `filters` (a IA é instruída a preferir soft delete via `deleted_at` quando a coluna existe) |
| `call_rpc` | Chama qualquer função RPC exposta pelo Supabase (ex: `stop_active_task`, `stop_task_log`) |

### Oversight

| Tool | Descrição |
| --- | --- |
| `recall_oversight_notes` | Lê notas geradas em segundo plano pelo oversight agent — padrões notados em lotes de moments, não só no que aconteceu nesta conversa |

Tabelas permitidas (`ALLOWED_TABLES` em `toolsCore.ts`): `fields`, `projects`,
`sections`, `tasks`, `task_items`, `task_logs`, `events`, `routines`,
`moments`, `moment_tags`, `work_tags`, `moment_tag_entities`,
`work_tag_entities`, `sections_sequence`, `tasks_sequence`.

`insert_row`/`update_rows` aceitam um parâmetro opcional `reason` — a
justificativa é anexada como `moment_note` ao moment que o próprio trigger
do banco já criou para essa mudança (`authored_by: 'assistant'`), fechando o
requisito de sempre documentar o contexto de uma mudança de status,
prioridade, due ou estimate.

`toolsCore.ts` também normaliza uma boa quantidade de variações que o
modelo emite na prática: nomes de tool alternativos (`update_row` →
`update_rows`), `filters`/`values` chegando como string JSON em vez de
array/objeto, `filters` chegando como mapa `{coluna: valor}` em vez de lista
de `{column, operator, value}`, `limit`/`ascending` como string.

## Reagindo a mudanças de banco fora do chat

Antes desta seção, a IA só "via" o que acontecia dentro da própria
conversa (ou, com ~15min de atraso e filtro de "digno de nota", via o
oversight agent). Marcar uma tarefa `done` no `TaskDetailModal`, por
exemplo, não chegava ao modelo de nenhuma forma. `src/lib/chat/
changeWatcher.ts` (lógica pura, testada) + `src/lib/chat/momentFeed.ts`
(fiação com o Supabase, injetável) + `src/hooks/useDbChangeFeed.ts` (liga as
duas) fecham esse requisito:

1. **Fonte**: `moments` está na publicação `supabase_realtime`; cada chamada
   de `subscribeToMomentFeed` (`momentFeed.ts`) assina `postgres_changes`
   (INSERT) nessa tabela. **Há exatamente um feed por página**, porque há
   exatamente um agente: `ChatAgentProvider` (`src/lib/chat/
   chatAgentContext.tsx`, montado no `AppShell`) é o único a chamar
   `useChatAgent`, e os `ChatPanel` são views dele. Isso é o que impede o
   watcher duplicado — dois feeds têm buffers, cooldowns e cursores de poll
   independentes, e o claim em `assistant_nudges` só desempata quando os dois
   fecham o lote no mesmo último moment. Cada chamada ainda recebe um tópico
   Realtime próprio (`'db-change-feed-<n>'`, contador de módulo) como defesa:
   `RealtimeClient.channel()` reaproveita o canal de um tópico já existente e
   `.on()` lança erro nesse canal se ele já estiver inscrito, o que derrubou o
   app inteiro quando duas instâncias de `ChatPanel` compartilhavam o tópico
   fixo — ver [Chat do assistente derruba o app ao abrir no
   mobile](backlog.md#chat-do-assistente-derruba-o-app-ao-abrir-no-mobile).
   Se a subscription não chegar a `SUBSCRIBED` em alguns segundos (Realtime
   pode estar desligado no projeto), ele cai para polling a cada 60s —
   degrada em vez de ficar mudo para sempre.
2. **Atribuição**: linhas com `authored_by = 'assistant'` são descartadas
   antes de qualquer outra coisa (ver `stampAssistantMoments` em
   `toolsCore.ts`, [Database](01-database.md#moments)) — sem isso o watcher
   reagiria à própria escrita do assistente. `useDbChangeFeed.ts` costumava
   *também* suprimir tudo que chegasse enquanto um turno estivesse em voo
   (mais uma janela de graça depois dele) para evitar que `onNudge` disputasse
   o mesmo `runWithUserContent` do turno em curso — isso tinha o efeito
   colateral de **perder** um lote que se fechasse durante um turno em vez de
   só esperar. Com a fila de turnos (`turnQueue.ts`), `onNudge` enfileira em
   vez de chamar o agente direto, então essa corrida não existe mais; a
   supressão foi removida e o filtro por `authored_by` sozinho já é
   suficiente.
3. **Buffer**: um lote de moments (um "marcar done" cascateia em vários)
   espera ~8s de silêncio antes de ser considerado fechado
   (`ChangeBuffer`).
4. **Gate determinístico**: antes de qualquer chamada ao modelo, o lote só
   segue se tiver pelo menos um moment "digno" — `status` → `done`/
   `cancelled`, `created`, `today`, `backlog`, `deleted`
   (`isNudgeWorthy`). `due`/`priority`/`renamed`/`moved`/`item`/`note` não
   disparam por si, mas viajam no resumo se estiverem no mesmo lote.
5. **Taxa**: cooldown entre nudges (`VITE_NUDGE_COOLDOWN_MINUTES`, default
   10min) e um teto por hora (`canNudge`).
6. **Disparo único**: antes de rodar o turno, o hook tenta inserir o id do
   último moment do lote em `assistant_nudges`; erro de chave duplicada
   significa que outra aba/instância já assumiu aquele lote exato — mesma
   ideia de idempotência de `telegram_notifications`.
7. **Turno**: `useChatAgent.ts` enfileira (`turnQueue.ts`) um turno
   silencioso (`runWithUserContent(..., {silent:true})`) com um prefixo
   `[DB Change: ...]` (ver `formatDbChangePrefix`) — tipo+id da entidade,
   tipo do moment, transição anterior→novo, autor. O prompt
   (`REACTING TO DATABASE CHANGES` em `prompts.ts`) autoriza explicitamente
   responder com nada, e instrui a propor uma próxima ação concreta (via
   `suggest_next_task`) em vez de narrar a mudança de volta. Se o modelo
   responder com texto, o badge de mensagem não vista acende
   (`markAssistantUnseen`), igual ao opener de sessão. Na UI, esse turno não
   aparece como bolha de usuário: `classifyTurnPrefix` (`turnPrefix.ts`)
   reconhece o prefixo contando profundidade de colchetes (em vez de um
   regex ancorado no primeiro `]`, que vazava resíduo ilegível quando o lote
   tinha mais de um moment — cada moment termina em `[user]`, que contém um
   `]` antes do `]` real do prefixo) e `ChatPanel` renderiza o lote como uma
   linha de atividade (ícone + frase + `EntityChip`), não como texto
   raspado.

## Adicionando uma nova tool

1. Adicione o schema em `READ_TOOL_DEFINITIONS`, `WRITE_TOOL_DEFINITIONS` ou
   `OVERSIGHT_TOOL_DEFINITIONS` em `toolsCore.ts`
2. Adicione o `case` correspondente em `executeTool`
3. Se a tool precisa ser usada pelo bot do Telegram também, nada extra é
   necessário — `toolsCore.ts` é compartilhado

## Dois front-ends, um cérebro

`src/lib/chat/*` (persona, schemas de tool, executor) é importado tanto pelo
app web quanto pela Edge Function `telegram-bot`
(`supabase/functions/_shared`), então os dois nunca divergem de
comportamento. O que muda entre eles:

| | App web | Telegram bot |
| --- | --- | --- |
| Chamada ao Claude | via Edge Function `anthropic-proxy` | direta, com `ANTHROPIC_API_KEY` |
| Client Supabase | anon key | service-role key |
| Confirmação de escrita | interativa na UI | nenhuma (bot single-owner atrás de allowlist) |
| Histórico | `chat_history` (compartilhado com o Telegram) | mesmo `chat_history` |

## Edge Functions

### `anthropic-proxy`

Reverse proxy que injeta `ANTHROPIC_API_KEY` do lado do servidor e repassa a
chamada para `api.anthropic.com`. `verify_jwt` fica desligado
(`supabase/config.toml`) porque o gateway bloquearia o preflight CORS antes
de a função rodar; em vez disso, a própria função valida
`Authorization: Bearer <supabase anon/publishable key>` manualmente.

### `telegram-bot`

Webhook do Telegram — responde mensagens com o mesmo agente/persona/tools do
app web. Client Supabase com service-role key, sem passo de confirmação de
escrita (allowlist de chat ids via `TELEGRAM_ALLOWED_CHAT_IDS`). Comandos:
`/start`, `/clear`, `/reset` (limpam o histórico), `/whoami` (retorna o chat
id, usado para configurar o allowlist inicialmente).

Diferente do app, o Telegram não tem renderer de card — mas também não
apaga mais os tokens `[[task:uuid]]`/`[[project:uuid]]`/`[[section:uuid]]`/
`[[event:uuid]]`: `renderForTelegram` (`_shared/khaos.ts`, lógica pura em
`_shared/telegramRender.ts`) resolve cada um com um `SELECT` service-role e
injeta um `<a href="KHAOS_APP_URL/...">nome</a>` (`parse_mode: 'HTML'`),
degradando para apagar o token quando `KHAOS_APP_URL` não está configurada
ou o id não resolve — nunca manda um link quebrado. Um `[[confirm: ...]]`
vira `inline_keyboard`; ver [Confirmação com botões](#confirmação-com-botões)
e o README do bot.

### `telegram-notify`

Disparada por cron, envia:

- **`digest`** — resumo matinal (atrasadas, vencem hoje, agenda do dia,
  janelas `scheduled` que passaram sem conclusão, `target` vencido,
  importantes não agendadas). Sugestões de ação ficam pendentes até o
  usuário responder aprovando.
- **`reminders`** — lembrete determinístico (sem chamada ao modelo) alguns
  minutos antes de um evento `scheduled` começar
  (`REMINDER_LEAD_MINUTES`, default 10).

Idempotente via `telegram_notifications`.

### `oversight-agent`

Rodando em cron (ex: a cada 15 min), varre `moments` desde o último cursor
salvo em `oversight_cursor`, agrupa em lotes por entidade e — quando um lote
é "digno de nota" (mais de um moment relacionado, ou um moment de tipo
`note`/`priority`/`status` sozinho) — pede a um modelo mais barato
(`claude-haiku-4-5` por padrão) um resumo curto, salvo em `oversight_notes`.
Só leitura para o chat interativo, via `recall_oversight_notes`; não existe
UI dedicada para essas notas.
